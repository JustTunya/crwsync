# CLAUDE.md

Guidance for working in this repository. This is a Turborepo/pnpm monorepo: `apps/frontend/web` (public Next.js portal), `apps/frontend/dash` (authenticated Next.js dashboard), `apps/backend` (NestJS API + Socket.IO gateway + BullMQ workers), and `packages/*` (shared `types`, `styles`, `templates`). See `PRODUCT.md` for product context and `DESIGN.md` for the visual system — this file is about how code gets written, not how it looks.

## Coding style

Match the existing code exactly. Do not "improve" formatting or add ceremony that isn't already the house style.

- **No inline or block comments**, with one narrow exception: a short trailing comment to clarify a magic number's unit (e.g. `300, // 5 minutes`). Do not add comments explaining what code does — names and structure carry that. Never leave commented-out code in a new change; if you find pre-existing commented-out blocks (e.g. `footer.tsx`), leave them alone unless the task is specifically about them.
- **Double quotes**, 2-space indentation, semicolons on statements. Follow whatever `prettier`/`eslint` (flat config at root `eslint.config.mjs`, `eslint-config-prettier` + `eslint-config-next`) would produce — run `pnpm lint` before considering a change done.
- **Compact over verbose.** Prefer a single well-named expression over a temp variable, a guard clause over nested ifs, `Promise.all` over sequential awaits when calls are independent. But never sacrifice readability for terseness — this codebase reads as dense-but-scannable, not golfed.
- **No unnecessary abstraction.** No interfaces with a single implementation, no factories for one product, no config objects for values that never change. Three similar lines beat a premature helper.
- **Naming:** `camelCase` for variables/functions, `PascalCase` for components/classes/types, `kebab-case` for file names (`use-workspace-modules.ts`, `ws-roles.guard.ts`), `SCREAMING_SNAKE_CASE` only for true module-level constants. Prisma/DB fields stay `snake_case` in schema and query shapes; everything else in TypeScript-land is `camelCase` — don't "fix" this mismatch by renaming one side.
- **Imports:** absolute via path aliases (`@/…` in each Next.js app, `src/…` in the backend, `@crwsync/types` / `@crwsync/styles` across the workspace) — never deep relative paths (`../../../..`) across module boundaries.
- **Types:** `strict: true` is on (`tsconfig.base.json`). Don't introduce `any` to route around a type error — narrow, assert with a real type guard, or fix the type. Shared domain types live in `@crwsync/types`, not duplicated per app.

## Efficiency & optimization paradigms already in place — extend, don't replace

- **Cache-first data access (backend):** Redis-backed `CacheService` with a centralized `CacheKeys` factory (`src/redis/cache-keys.ts`) and `CacheTTL` constants. Every new read path that's hit repeatedly (per-request auth/session lookups, workspace membership checks) should go through this cache, and every mutation that changes cached data must explicitly invalidate the specific keys it affects (see `invMembershipCaches` in `workspace.service.ts`) — never a blanket cache flush.
- **Query-key factories + `staleTime` (frontend):** TanStack Query hooks are grouped behind a `xKeys` object (`workspaceKeys`, `boardKeys`, `moduleKeys`, …) with `all/list/detail/…` helpers, and reads set an explicit `staleTime` (commonly 5 minutes) instead of refetching on every mount. New data hooks follow this exact shape — don't hand-roll ad hoc query keys as raw arrays inline.
- **Optimistic UI + WebSocket reconciliation:** Dashboard mutations update the UI immediately and reconcile via REST response; real-time state from other users arrives over Socket.IO and patches the same React Query cache directly (`queryClient.setQueryData`) rather than triggering a full refetch — full invalidation is the fallback only when a socket payload doesn't carry enough data to patch precisely (e.g. `board:task:moved`). Follow the existing `use-*-socket.ts` pattern (singleton socket from `socket.provider.tsx`, listeners registered/cleaned up in one `useEffect`) rather than opening new connections per component.
- **Horizontal scalability by construction:** Socket.IO uses a Redis adapter (`RedisIoAdapter`) so WebSocket state fans out across instances — never assume in-process state is authoritative for anything socket-related; the source of truth is Postgres/Redis, not a gateway's local memory.
- **Database access:** Prisma `select`/`include` are shaped explicitly per query (see `src/prisma/selects.ts` and inline `select` blocks) to avoid over-fetching — don't return full Prisma models to the client by default. Multi-step writes that must be atomic use `prisma.$transaction`. Favor a single query with the right `include`/`select` over N+1 round trips.
- **Global HTTP concerns are centralized, not per-route:** `helmet`, `compression`, a global `ValidationPipe` (`whitelist: true, forbidNonWhitelisted: true, transform: true`), a global `AllExceptionsFilter`, and global `LoggingInterceptor`/`TimeoutInterceptor` are wired once in `main.ts`. New cross-cutting concerns (rate limiting, request shaping, error formatting) belong there or as a new global provider — not sprinkled into individual controllers.
- **Per-route throttling is tuned, not default:** `@Throttle({ default: { ttl, limit } })` / `@SkipThrottle()` are set per-endpoint based on actual sensitivity (5/hour on workspace creation, 50/hour on invites, `@SkipThrottle()` on cheap idempotent reads). Match this granularity for new endpoints instead of leaving everything on one global limit.

## High-level architectural paradigms

- **Guard/decorator composition over inline checks (backend):** authorization is expressed as a stack of `@UseGuards(...)` + a `@RequireWorkspaceRoles(...)` decorator, not `if` statements inside service methods checking roles. Add new authorization rules as guards/decorators, and keep services focused on business logic that assumes the request already passed authorization.
- **Controllers stay thin.** A controller method is a one-line delegation to the service (`return this.workspaceService.x(...)`); parameter parsing/validation happens via pipes (`ParseUUIDPipe`, DTOs) and decorators (`@ActiveUserParam()`), not by hand in the method body.
- **Service layer on the frontend mirrors the backend's response shape.** Every `services/*.service.ts` function returns a discriminated `{ success, data?, message?, errors? }` result (`WorkspaceOperationState<T>` and friends from `@crwsync/types`) and never throws past its own `try/catch` — callers (hooks) are the ones that turn a `{ success: false }` into a thrown `Error` for React Query. Keep this boundary: services normalize errors, hooks/mutations decide what to do about them.
- **Separation of deployable services is real, not cosmetic.** `web`, `dash`, and `backend` are independently deployable; don't reach across app boundaries with relative imports or shared runtime state — cross-app sharing only happens through `packages/*` or the network (REST/WebSocket).
- **Real-time is additive to REST, never a replacement.** REST/HTTP remains the authoritative write path; Socket.IO exists purely to propagate confirmed state to other connected clients. New realtime features should follow this same shape (mutate via REST, broadcast via gateway, patch cache on receipt) — see `plant.md` for the reference design of this pattern.
- **Background work goes through BullMQ**, not inline in a request handler, whenever it's not required for the response (email delivery, scheduled cleanup). Don't block a request/response cycle on side-effect work that can be queued.
- **Fail fast on missing required config.** `main.ts` exits the process if `CORS_ORIGIN` isn't set rather than booting into an insecure default. Apply the same standard to any new required environment variable — validate at startup, not at first use.
